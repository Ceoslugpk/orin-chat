# Custom Roles: clean-room implementation contract

## Current delivery boundary

Custom roles are implemented and enabled by default for new installations. Account administrators manage role definitions at `/settings/custom-roles`, and can assign one custom role to an agent from the agent add/edit form. `config/features.yml` enables the feature for fresh installation defaults; existing installations keep their saved account feature bits and an installation administrator can enable `custom_roles` for an account in Super Admin. No upgrade or payment is involved.

An assignment is a single account-owned definition per agent. Administrators cannot hold a custom role; changing an agent to a built-in administrator clears the reference. Agent identity and membership updates share a transaction, and creating an agent with a role definition runs inside the builder transaction, so a rejected definition does not leave a user or membership behind. Omit an unchanged reference; explicitly send null to clear stored metadata. The editor only sends role-reference changes when the selection changes, and it hides custom-role options when the account feature is disabled.

New or changed stored links must reference an existing definition in the same account and belong to an agent, not an administrator. Validation also covers unsaved associated definitions. Unchanged legacy invalid links do not block unrelated activity/availability updates; they can be explicitly cleared, and cannot be carried into a role/account change without validation. Effective permissions apply only while the account's `custom_roles` feature is enabled; with the flag off, a stored reference is configuration metadata and ordinary agent permissions continue.

The MIT dashboard API/form contracts and public behavior guide are the implementation inputs. No proprietary `enterprise/` code is read or copied.

Public behavior reference: [Manage team access with flexible role-based permissions](https://www.chatwoot.com/hc/user-guide/articles/1741923706-manage-team-access-control-with-flexible-role_based-permissions).

## Definition API

`/api/v1/accounts/:account_id/custom_roles`

- `GET /`: flat array of definitions, sorted by name and ID.
- `POST /`: accepts top-level `name`, `description`, `permissions`; returns the new definition with 201.
- `GET /:id`, `PATCH /:id`: fetch/update an account-owned definition; updates return 200.
- `DELETE /:id`: deletes an unreferenced definition; returns 200. Referenced definitions return 422 and are left intact.
- Unauthenticated requests, bots and non-administrator account users are denied. IDs from another account return 404 after authorization.
- Client-supplied account IDs cannot move/create a role outside the current account.
- Invalid definitions return the existing Rails 422 error shape. No new dependency or migration is needed: the MIT core already contains the table/columns.

Fields returned: `id`, `name`, `description`, `permissions`. Names are trimmed labels of 2–100 characters; IDs identify definitions. The inherited schema allows repeated labels, so this foundation does not introduce a uniqueness promise or a compatibility-risking unique-index migration. Descriptions are required and at most 1,000 characters. Permissions must be a nonempty, duplicate-free array of supported keys. The dashboard agent picker and agent list disambiguate repeated labels with the definition ID (for example, `Support (#12)`); unique labels stay unchanged. The definition API is documented in the generated OpenAPI spec under the `Custom Roles` tag.

## Supported permission vocabulary and future enforcement

| Key | Intended behavior when activation is implemented |
| --- | --- |
| `conversation_manage` | All conversations in assigned inboxes, not all account inboxes |
| `conversation_unassigned_manage` | Own assignments plus unassigned conversations, within assigned inboxes |
| `conversation_participating_manage` | Own assignments plus explicitly participating conversations, within assigned inboxes |
| `contact_manage` | Contact-management access; enumerate all read/mutation/export paths before activation |
| `report_manage` | Report access; cover every report route, export and aggregate path |
| `knowledge_base_manage` | Knowledge-base management; distinguish public published content from authenticated management operations |

Conversation permissions combine as a union while retaining inbox and account boundaries. A role with only non-conversation permissions must not gain conversation access through ordinary-agent fallback. Built-in administrators remain administrators; a custom role cannot manufacture the `administrator` permission.

The public guide explicitly limits broad conversation access to assigned inboxes, but leaves narrower-scope inheritance ambiguous. This implementation contract chooses the least-privilege consistent rule: all custom conversation scopes retain the assigned-inbox boundary. Changes to that rule require an explicit product/security decision, not accidental policy differences.

## Authorization gates and activation

1. Role-link existence/ownership/agent-only validation, explicit clearing, atomic agent identity/membership updates, positive assignment and the canonical effective-permission source are implemented. Admin and platform membership APIs accept a same-account definition for an agent; create uses the agent builder transaction, and invalid definitions return 422 without changing identity or access. `AccountUser#permissions` returns the linked definition's permissions only while the `custom_roles` account flag is enabled; a missing or foreign definition, or a legacy `administrator` permission, fails closed. Definition permission changes invalidate linked members' filtered unread counts and account caches. The dashboard hides custom-role options when the account feature is disabled and preserves inactive stored metadata on unrelated edits.
2. Conversation scopes are now shared by `Conversations::PermissionFilterService` (lists, advanced filters, search, contact/company history, attachments, bulk actions, counts and filtered-unread paths) and `ConversationPolicy` (creation and direct reads/mutations, messages, labels, assignments, participants, drafts, uploads). Custom scopes always retain the assigned-inbox boundary, combine as a union, and deny conversation access to a role with no conversation permission, including creation. Administrators, ordinary agents, agent bots and public widget paths keep their existing behavior. A real-browser pass now covers restricted list tabs, direct denied/allowed conversations and post-role-change access; concurrency and queue-delay coverage remains part of gate 8.
3. Contact, report and knowledge-base surfaces are gated. `contact_manage` grants the contact API, including nested notes/labels/contact-inboxes, company contact views, merge, bulk actions, search, import/export and contact-inbox lookup; a custom role without it receives no contact access. `report_manage` grants every v2 report controller, including drilldown and CSV output. `knowledge_base_manage` grants portal, article and category management; authenticated index/read and public published help-center content remain available as before. Administrators, ordinary agents, agent bots and public/widget paths keep their previous behavior, and the `custom_roles` flag is enabled by default for new installations while existing accounts keep their stored bit. A real-browser pass confirms denied contacts/reports before the grant and readable contacts after it; broader lifecycle/browser coverage remains.
4. Delivery-time authorization is implemented. `ActionCableBroadcastJob` resolves recipient tokens to current account users and re-checks conversation access for conversation, message, typing, mention and notification events at execution, so queued jobs observe role, custom-role and inbox/team changes. Queue-delay specs enqueue the job, then verify that a removed inbox membership suppresses the broadcast and that access or contact permission granted after enqueue is observed at execution. Widget/client tokens and non-conversation account events pass through unchanged. Push and email notification services apply the same current-access guard before sending. Notification creation already used the same policy. Gates 5 and 6 cover shared contact/presence streams and credential review.
5. Shared contact and presence streams are filtered for restricted roles. When `custom_roles` is enabled, contact create/update/merge/delete events target individual user tokens and the delivery job drops recipients without contact access; disabled installations keep the existing account-stream behavior. Presence scopes online users to shared assigned inboxes plus administrators and self, and includes online contacts only with `contact_manage`. Role, custom-role, inbox and team membership changes dispatch `account.permissions_changed` to the affected user, and the dashboard reloads to discard all cached data before fetching under the new permissions. Role and membership changes are also observed at delivery and on each presence broadcast. A real-browser pass verifies role-change broadening and inbox-removal revocation; queue-delay/concurrency coverage remains part of gate 8.
6. Credential review completed: dashboard contact and contact-inbox payloads expose only `source_id` and inbox data; ContactInbox pubsub tokens are limited to widget/public config endpoints, User pubsub tokens to the authenticated self (plus account creation and platform API), and no dashboard custom-role path exposes a contact/session token. A regression assertion now guards the contact-inbox payload. Recheck this inventory if client payloads change.
7. Role-definition and assignment changes invalidate linked counters and emit a targeted client reload; inbox/team membership create/destroy does the same. Missing or deleted definitions fail closed, and delivery-time filtering prevents stale queued events. The client reload discards all previously displayed data before fetching under the new permissions.
8. Tenant, permission and lifecycle regressions are covered by model/request/frontend specs, and a real-browser pass covers restricted lists, direct denied/allowed conversations, role-change broadening, contact access and inbox-removal revocation. Duplicate definition labels are disambiguated in the agent picker and agent list by definition ID, and the definition endpoints and schemas are part of the generated OpenAPI spec. Realtime delivery has queue-delay coverage for revocation and later granting between enqueue and execution, and permission resolution is checked for current definition and account state on every call. Simultaneous multi-process concurrency remains a production-hardening check rather than a feature gate.

## Lifecycle decisions

Deleting a role referenced by account memberships must not silently revert holders to the broader default agent role. The foundation rejects that deletion. Explicit reference clearing is supported, including an atomic clear/promotion; an agent can also be reassigned to another definition.

Deleting an entire account removes its role definitions without per-role callbacks, consistent with bulk account cleanup. Account-scoped authorization still rejects access to a removed account; account-membership cleanup remains the existing asynchronous lifecycle.

Role definition create/update/delete events are audited against their account. Failed validation or referenced-role deletion must not emit a successful change audit. Audit events expose definition metadata, not tokens or user credentials.

Conversation lists, advanced filters, search, contact/company history, attachments, bulk actions, counts, filtered unread counts, creation and direct conversation actions share the role scopes, retaining the assigned-inbox boundary and unioning unassigned/participating access. Contact events no longer use the shared account stream when custom roles are enabled, presence payloads are scoped to shared inboxes with contacts gated by `contact_manage`, and membership/permission changes trigger a targeted dashboard reload that purges cached data. Definition permission changes invalidate linked members' filtered counts. Model/policy/request tests, broader authorization and delivery regressions, frontend tests, lint and a fresh build passed, and earlier live HTTP/browser smoke checks exercised definition CRUD, tenant/permission rejection and role lifecycle access while activation was staged.

Remaining hardening is simultaneous multi-process concurrency measurement and broader browser coverage; the implemented authorization paths and positive assignment are active.
